# الأوامر والسكربتات

جميع الأوامر تُنفَّذ عبر **Bun** حصراً.

## سكربتات `package.json`

| السكربت | الأمر | الوظيفة |
| --- | --- | --- |
| `dev` | `bun dev` | خادم التطوير مع إعادة التحميل الفوري |
| `build` | `bun run build` | بناء نسخة الإنتاج (`next build`) |
| `start` | `bun run start` | تشغيل نسخة الإنتاج بعد البناء |
| `lint` | `bun run lint` | فحص الكود بـ ESLint |
| `docs:check` | `bun run docs:check` | فحص التوثيق: ترويسات، ترتيب، وروابط داخلية |
| `engine:check` | `bun run engine:check` | تحقق سلوكي من محرك الفحص (انزياح، سند، حكم، سجل) |
| `benchmark` | `bun run benchmark` | تشغيل مدوّنة القياس (٣٧ زوجًا) على المحرك الحقيقي وكتابة `data/benchmark/results.json` |
| `retrieval:check` | `bun run retrieval:check` | فحص **المسترجِع الحيّ** عبر المحرك بخمس حالات، بطلبات شبكية فعلية |
| `build:worker` | `bun run build:worker` | بناء Worker لنشر Cloudflare (OpenNext) |
| `preview` | `bun run preview` | معاينة Worker محليًا |
| `deploy` | `bun run deploy` | نشر Worker على Cloudflare |
| `cf-typegen` | `bun run cf-typegen` | توليد أنواع Cloudflare (`wrangler types`) |
| `preinstall` | يُنفَّذ تلقائياً | حارس Bun-only (لا يُشغَّل يدوياً) |

## أوامر إدارة الاعتماديات

```bash
bun install            # تثبيت جميع الاعتماديات من bun.lock
bun add <pkg>          # إضافة اعتمادية إنتاج
bun add -d <pkg>       # إضافة اعتمادية تطوير
bun remove <pkg>       # إزالة اعتمادية
bunx <tool>            # تشغيل أداة لمرة واحدة (بديل npx)
```

## سير عمل التحقق الإلزامي

قبل أي دفع (push)، شغّل:

```bash
bun run lint            # يجب أن يمرّ بلا أخطاء
bun run docs:check      # يجب أن يمرّ بلا ترويسات ناقصة ولا روابط مكسورة
bun run engine:check    # يجب أن تمرّ كل حالات المحرك
bun run retrieval:check # فحص المسترجِع الحيّ عبر المحرك (يحتاج شبكة)
```

هذه تحقّقات ما قبل الدفع الأربعة، وتُضاف إلى خطوة التحقّق في
[سير العمل الإلزامي](/docs/reference/conventions#سير-العمل-الإلزامي) التي تطلب `bun run lint` ثم
`bun run build` عند اللزوم.

> `bun run build` و`bun run build:worker` يملكهما مسار البناء، ولا يلزم تشغيلهما لتغيير توثيقي.
> و`bun run retrieval:check` وحده من الأربعة يخرج إلى الشبكة؛ فإن تعذّر الوصول إلى المصدر عُدّ
> ذلك فشلًا معلنًا لا نجاحًا صامتًا.

## `bun run retrieval:check` — ماذا يفعل ومالا يفعله

سكربت «scripts/live-retrieval-check.ts» يفحص **طبقة الاسترجاع الحيّة** عبر المحرك الحقيقي
(`runAudit`)، بخمس حالات:

1. **آية نُقلت حرفيًا** → واقعة `preserved` تحمل إحالة «quranpedia» بآيةٍ (`2:153`) وعنوانٍ ولحظة
   قراءة، والسجل المختوم يقبل التحقق.
2. **الآية نفسها بحرف واحد مغيَّر** → واقعة `shifted` مثبّتة على الآية (`2:153`)، والحكم ليس
   `faithful`.
3. **آية أُسقطت** من النص المشتق → واقعة `missing`.
4. **نص يشبه الاقتباس وليس من القرآن** → لا تُختلق واقعة، بل **ملاحظة تغطية** تشرح أن الموضع لم
   يُربط (وهذا ليس حكمًا بأنه خطأ).
5. **عدّ الطلبات الصادرة** في تشغيل واحد → «2» طلبات، دون السقف المعلن «33».

### الفرق بينه وبين `engine:check`

`engine:check` يشغّل المحرك **بلا شبكة** عن قصد: يمرّر إليه مسترجِعًا مزيّفًا حتميًا (ونموذجًا مدسوسًا
في بعض الحالات)، فتصبح نتائجه قابلة لإعادة الإنتاج بالكامل ومجانية. لكن هذا يعني أن **لا حالة فيه
تُثبت أن الموصلات الحقيقية تعمل حين يستدعيها المحرك**. `retrieval:check` يسدّ هذه الفجوة: يشغّل
`runAudit` **بالمسترجِع الافتراضي الحيّ** (بلا تمرير مسترجِع)، فيمرّ الطلب فعليًا عبر
«api.quranpedia.net». ولهذا ضبط الإصلاحان اللذان وثّقتهما
[صفحة القياس](/docs/reference/measurement): إنذاران لا يظهران إلا عند لمس الشبكة، ولم يكشفهما المسترجِع
المزيّف. الأثر أن الفحصين متكاملان لا متكرران: أحدهما للحتمية، والآخر للموصل الحقيقي.

## أوامر مستحسنة

```bash
bun dev -- -p 3001     # تشغيل على منفذ مختلف
bunx tsc --noEmit      # تحقّق أنواع يدوي (بدون إخراج)
```

> **تذكير:** أي أمر يعتمد على `npx` يجب استبداله بـ `bunx`، وأي تثبيت يجب أن يبدأ بـ `bun`.
